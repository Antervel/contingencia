# E1-02: Fake `main` and fake outside world (SMTP sink)

**Epic:** E1 (mta + imap prototype)
**Size:** S
**Depends on:** E1-01
**Hypotheses covered:** supports H8, H9

## Context

The appliance is a backup for `main`. To test an outage we need a stand-in for `main` that we can **switch off and on**, and that **records exactly what it receives** so we can check the original messages arrive unmodified. For submission tests (E1-08) we also need a stand-in for "the rest of the internet" that receives outgoing mail. In the prototype both roles are played by the same sink container, to keep the stack small.

## What to do

1. Choose the sink. Requirements:
   - Accepts SMTP on port 25 for **any** recipient and **any** sender, with no authentication and no spam checks.
   - Stores every received message **in full, byte for byte** (raw message including all headers), and lets us list and read them from the host (a web page, an API, or files in a volume).
   - Can be stopped and started with `docker compose stop main` and `docker compose start main`, and while stopped, connections to it must be **refused or time out**, as if the server were down.
   An existing, ready-made SMTP testing image fits (for example a tool like Mailpit). If you use an existing image, record the exact image and tag in `docs/FINDINGS.md`. If none fits, a very small script that listens on port 25 and writes raw messages to a folder is acceptable. Do not spend more than the ticket's estimate on building one.
2. Add it to `compose.yaml` as the `main` service (replace the placeholder from E1-01).
3. Publish its viewing interface on `127.0.0.1` only, and its SMTP port on host `2526`.
4. Decide **how tests will inspect received mail** and write it down in the ticket's notes, for example: "list messages with curl against the API, and fetch the raw source of message N". This method is reused by every later ticket.
5. Write a small helper script `prototype/tests/lib/sink.sh` (or similar) with three operations, to be reused by E1-11:
   - `sink_count`: print how many messages the sink holds.
   - `sink_clear`: delete all stored messages.
   - `sink_raw N`: print the raw source of message number N.
6. Check the sink with a direct test message from the host (not through `mta`).

## Acceptance criteria

- `docker compose up -d main` starts it. A test message sent to `localhost:2526` appears in the sink.
- The raw source of the message is retrievable and identical to what was sent (compare a checksum of the sent file with the stored one, allowing for any headers the sink *adds*, which must be documented).
- After `docker compose stop main`, a connection attempt from `mta` (use `docker compose exec mta` with a simple TCP check) fails. After `docker compose start main`, it succeeds again.
- The helper operations `sink_count`, `sink_clear` and `sink_raw` work from the host.
- `docs/FINDINGS.md` lists the sink image and version, and any headers the sink adds to stored messages.

## How to test

```
# From the host, with a throwaway message
swaks --server 127.0.0.1:2526 --from test@sender.test --to anyone@client.test --body "direct test"
prototype/tests/lib/sink.sh count          # expect 1
prototype/tests/lib/sink.sh raw 1          # expect the message
docker compose stop main
swaks --server 127.0.0.1:2526 --to anyone@client.test ; echo "exit code: $?"    # expect failure
docker compose start main
```

If `swaks` is not available, any command-line SMTP client works. Record which one is used, because every later ticket uses it as well.

## Notes and pitfalls

- A sink that **accepts the connection but queues internally while "stopped"** would hide outages. Make sure stopping really stops listening.
- If the sink rewrites or normalizes messages, the "unmodified" check in E1-07 becomes meaningless. Read how it stores raw messages and prove it does not alter them.
- The same sink receiving outgoing mail in E1-08 means the tests must filter by recipient domain (`outside.test` vs `client.test`) when counting.
