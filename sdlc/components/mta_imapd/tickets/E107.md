# E1-07: Outage and recovery scenario

**Epic:** E1 (mta + imap prototype)
**Size:** M
**Depends on:** E1-05
**Hypotheses covered:** H8

## Context

The product's reason to exist is surviving an outage of `main` and handing over everything afterwards. This ticket exercises the full timeline: `main` goes down, mail arrives, users read their copies, `main` returns, and the queued originals are delivered. It must also show that nothing is lost when the backup itself restarts, and that the queue behaves sensibly over time.

## What to do

1. **Baseline timeline.** Run this end to end and capture evidence at each step:
   1. `main` up. Send 1 message to `alice@client.test`. It reaches the sink. Alice has a copy.
   2. Stop `main`. Send 5 messages to alice, 3 to bob, 2 to `nobody@client.test` (catch-all). Each user's copies appear immediately in their INBOX.
   3. `postqueue -p` shows exactly 10 queued originals, each with a deferral reason.
   4. Start `main`. Within one retry interval (or after `postqueue -f`), the sink receives all 10 originals.
   5. After delivery the queue is empty and no copy was ever queued.
2. **Fidelity.** For two of the delivered originals, compare the raw message in the sink to the original that the sender transmitted. Differences must be limited to added `Received:` headers (and any header the sink itself adds). The body, `From`, `To`, `Subject`, `Date` and `Message-ID` must be identical. Record the result and any extra header.
3. **Natural retry.** Do **not** flush the queue in one run. Measure how long Postfix takes to retry after `main` returns, by default. Record the retry intervals Postfix is using (`minimal_backoff_time`, `maximal_backoff_time`, `queue_run_delay`). If the default retry delay is long (minutes to hours), decide whether the admin service's "flush queue" button (PRD FR-19) is enough, or whether to lower the backoff timers. Record the recommendation.
4. **Backup restart during outage.** With `main` down and messages queued, run `docker compose restart mta` and confirm the queued messages are still present. Repeat with `docker compose down` followed by `up` (not `-v`, so volumes persist).
5. **`imap` restart.** Restart `imap` and confirm mail copies are intact.
6. **Concurrent arrivals.** Send 50 messages in parallel to different recipients while `main` is down, using a simple loop with background jobs. Confirm that the queue shows 50 originals and that each mailbox has the right number of copies. This is a sanity test, not a load test.
7. **Queue lifetime setting.** Confirm `postconf maximal_queue_lifetime` shows `100d`. Do **not** wait 100 days. Instead, prove the setting is effective by temporarily setting a very short lifetime (for example 2 minutes) in a throwaway test, observing that an undeliverable message then bounces, and restoring 100d. Capture the bounce message and record where it goes (to the sender, as it should).
8. **Disk usage per queued message.** Record how much queue disk each message uses, to support the "size the queue volume" note in the PRD risks.

## Acceptance criteria

- **H8 PASS:** the baseline timeline holds: copies appear instantly during the outage, all originals arrive after recovery, nothing is lost, and the queue empties.
- Originals are delivered unmodified apart from added transport headers.
- Queued messages survive `mta` restart and a full stop and start of the stack.
- The 50-message concurrency test ends with consistent counts.
- The short-lifetime test shows a bounce, and the lifetime is restored to 100d afterwards (verify with `postconf`).
- The default retry timing and a recommendation are recorded in `docs/FINDINGS.md`.
- Evidence stored in `docs/evidence/E1-07/`.

## How to test

```
docker compose stop main
for i in 1 2 3 4 5; do swaks --server 127.0.0.1:2525 --from s@sender.test --to alice@client.test --header "Subject: outage $i" --body "n$i"; done
docker compose exec mta postqueue -p | tail -3
docker compose restart mta
docker compose exec mta postqueue -p | tail -3            # same count
docker compose start main
sleep 5; docker compose exec mta postqueue -p | tail -3    # may still hold items: record how long until empty
docker compose exec mta postqueue -f
prototype/tests/lib/sink.sh count
docker compose exec mta postconf maximal_queue_lifetime bounce_queue_lifetime minimal_backoff_time maximal_backoff_time queue_run_delay
```

## Notes and pitfalls

- Resetting `main` by stopping and starting it may **clear** the sink's stored messages if it keeps them in memory. If so, export or count messages before stopping it, or give the sink persistent storage. Do not mistake a lost record for lost mail.
- Postfix delays retries after failures, and it does so **per destination**. After a long outage, retries may be far apart. This is exactly why the retry behavior is measured here.
- Never use `docker compose down -v` in this ticket, because it deletes the queue volume and invalidates the test.
