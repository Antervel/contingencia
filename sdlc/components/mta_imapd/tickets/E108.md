# E1-08: Authenticated submission, sender enforcement, rate limit

**Epic:** E1 (mta + imap prototype)
**Size:** L
**Depends on:** E1-03, E1-05
**Hypotheses covered:** H9

## Context

Users send mail from webmail. Webmail will connect to `mta` on port 587 with the user's own login (`alice@client.test` and password), and `mta` must:

1. **Authenticate** the user. Postfix does not store passwords, so it asks Dovecot, in the other container, over the private network.
2. **Allow only that user's own address as sender.** `alice@client.test` may send as `alice@client.test`, never as `bob@client.test`.
3. **Limit the sending rate** to 1 message per second, as a protection against a compromised mailbox. Because all webmail traffic comes from one container address, the limit applies to all users combined (decision recorded in `technical.md`).
4. **Deliver outgoing mail** to its recipients. In the prototype, "the outside world" is the sink, reached by routing `outside.test` there.

DKIM signing is **not** part of this ticket (Epic 2). Port 587 must work correctly without it, and the configuration must leave a clean place to attach it later (a milter setting on this service only).

## What to do

### Part A: Authentication through Dovecot

1. In Dovecot, make the **authentication service** available to Postfix over TCP on the private network (the port chosen in E1-03). Confirm it is **not** published to the host.
2. In Postfix, define the **submission service** on port 587 in `master.cf`:
   - SASL authentication required, using Dovecot's authentication service over the network.
   - Encryption not required in the prototype, because the network is private.
   - Relaying allowed **only** for authenticated users.
   - Unauthenticated clients rejected for any recipient.
3. Test login success and failure with both `AUTH PLAIN` and `AUTH LOGIN`.

### Part B: Sender enforcement

4. Create a table `/config/postfix/sender_login` mapping each sender address to the login name allowed to use it:
   - `alice@client.test` is allowed for login `alice@client.test`
   - `bob@client.test` for `bob@client.test`
   - `carol@other.test` for `carol@other.test`
   - the catch-all mailbox `_catchall@client.test` for itself
   Configure Postfix to use it and to **reject** a mismatch.
5. Test:
   - alice logs in and sends as alice: accepted.
   - alice logs in and sends as bob: rejected at SMTP time with a clear message.
   - alice sends with a sender address that is not listed at all (`ceo@client.test`): rejected.
   - alice sends with an empty sender (`<>`): decide and record the behavior (normally rejected for authenticated users).
6. Check that the sender check does **not** apply to port 25. A normal external sender may use any `From` address on port 25.

### Part C: Rate limit

7. Configure the submission service with a limit of **1 message per second**. Postfix's rate counting works with a count per time window, per client address; work out the exact parameter values that give an average of one message per second and record the reasoning (including the window size and whether bursts are allowed).
8. Test with a loop of 10 rapid submissions as one user, and observe: some are delayed or rejected with a temporary error. Record the exact SMTP response seen by the client. A temporary (4xx) response, which asks the client to retry, is preferable to a permanent rejection for a legitimate sender. Document which one the configuration produces.
9. Test with two users submitting at the same time to confirm that the limit is combined across users (the known and accepted behavior). Record the result.
10. Confirm that the limit applies **only** to the submission service and never to mail received on port 25. Send 20 messages quickly to port 25 and show none are limited.

### Part D: Outgoing delivery and loops

11. Send as alice to `friend@outside.test` and confirm the message reaches the sink, without a copy being made (copies are for **incoming** mail to client mailboxes).
12. Send as alice to `bob@client.test` (internal to the same client). Observe and record: the original is queued toward `main` (it is a relay domain), **and** the BCC rule makes a copy for bob. Whether alice's own sent mail should also be kept is a webmail matter, not a mail-server one.
13. Send as alice to `nobody@client.test` and confirm the catch-all behavior is consistent with E1-06.

## Acceptance criteria

- **H9 PASS (authentication):** login through Dovecot over the network works for the right password and fails for others. The authentication port is not reachable from the host.
- **H9 PASS (enforcement):** a user can send only as their own address; other senders are rejected at SMTP time.
- **H9 PASS (rate):** the combined limit of about 1 message per second is demonstrated, with the exact parameters and observed SMTP responses recorded.
- The port 25 behavior is unchanged: no authentication needed, no sender-login check, no rate limit.
- Outgoing mail to `outside.test` reaches the sink; mail between client mailboxes behaves as in step 12.
- The `master.cf` entry for the submission service has a clearly marked spot where the DKIM milter option will be added in Epic 2, and the file says so in a comment.
- Evidence stored in `docs/evidence/E1-08/`.

## How to test

```
# Authentication
swaks --server 127.0.0.1:5587 --auth-user alice@client.test --auth-password alice-pass \
      --from alice@client.test --to friend@outside.test --body "hello"
swaks --server 127.0.0.1:5587 --auth-user alice@client.test --auth-password WRONG \
      --from alice@client.test --to friend@outside.test ; echo "exit: $?"

# Sender enforcement
swaks --server 127.0.0.1:5587 --auth-user alice@client.test --auth-password alice-pass \
      --from bob@client.test --to friend@outside.test ; echo "exit: $?"      # expect rejection

# Rate limit
for i in $(seq 1 10); do
  swaks --server 127.0.0.1:5587 --auth-user alice@client.test --auth-password alice-pass \
        --from alice@client.test --to friend@outside.test --body "n$i" --quit-after RCPT &
done; wait

# Port 25 unaffected
for i in $(seq 1 20); do swaks --server 127.0.0.1:2525 --from x@sender.test --to alice@client.test --body "n$i" & done; wait

# From inside the stack: check the auth port is not published to the host
ss -ltn | grep 12345 ; echo "published on host? (expect nothing)"
```

## Notes and pitfalls

- Postfix's rate limit counts **messages per client per time unit**, where the time unit is a global setting also used by other limits. Read the documentation for the exact parameter semantics before choosing values, and test the actual behavior rather than trusting the arithmetic.
- The rate limit is intended to catch abuse, not to hurt real users. If a normal user clicking "send" twice in a row is blocked in an annoying way, that is a finding.
- If authentication over TCP is unreliable or complicated in the Dovecot setup, the documented fallback is a Unix socket shared between containers by a volume (see epic fallback F9). Do not apply it without recording evidence of the problem.
- Ports bound to `127.0.0.1` for testing can hide a missing restriction. Also test from another container on the Compose network (`docker compose exec`), because the final system relies on the network, not on host bindings, for isolation.
