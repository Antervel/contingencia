# E1-09: Configuration reload behavior

**Epic:** E1 (mta + imap prototype)
**Size:** M
**Depends on:** E1-06, E1-08
**Hypotheses covered:** H5, H6

## Context

In the finished system, the Rust `admin` service rewrites configuration files and then makes the running services notice. How it does that (which command, in which container, in which order) is the heart of its "apply pipeline" (`technical.md` section 4.4). The service must do **the minimum necessary** after each kind of change, and must be able to verify that the change took effect.

This ticket finds out, by experiment, **exactly** what each kind of change requires. The output is a table the admin service author follows literally.

## What to do

For each change below, work through the same procedure:

1. State the change and the files it touches.
2. Make the change **without** any reload. Test whether the running service already sees it. Record yes or no.
3. If not, try the **lightest** reload (Postfix: `postfix reload`; Dovecot: `doveadm reload`). Record whether it is enough.
4. If not, try a **service restart** (restart the container). Record whether it is enough.
5. Record the **exact verification command** that proves the change is active, which the admin service will run after applying it.
6. Record any **side effects** during the reload (dropped connections, mail deferred, queue disturbed).

For each Postfix change, the verification command should be a **lookup** that proves the change is in effect (for example a table lookup through the running Postfix, or a test message that exercises the rule). For each Dovecot change, it should be `doveadm user` for both names and, for passwords, `doveadm auth test`.

### Atomicity and partial states

7. Test what happens when a file is **replaced while Postfix is delivering**: write the new table file to a temporary name in the same folder and **rename** it over the old one (an atomic replace), compared with editing in place. Record whether a half-written file can ever be seen, and conclude that the admin service must always write by rename.
8. Test what happens when the **new file has a syntax error** (for example, a table line with no value). Observe what Postfix and Dovecot do: continue with the old data, reject mail, or crash? This tells the admin service whether to rely on rollback after a failed verification.
9. Test the **rollback**: restore the previous file and reload, then verify that the old behavior is back.
10. Test a **mailbox directory deletion**: after removing a mailbox from the user file, deleting its Maildir from inside `imap` (planned `admin` behavior) while Dovecot is running. Observe any errors in the logs.

## Acceptance criteria

- **H5 PASS or CHANGED:** each Postfix table type used works with `texthash:` and the minimal reload for each change is recorded. If any table needs `hash:` and a `postmap` step, that is recorded as CHANGED, with the reason.
- **H6 PASS or CHANGED:** the minimal reload for each Dovecot change is recorded.
- A **reload table** exists in `docs/FINDINGS.md` with one row per change P1 to P10 and D1 to D4, with columns: "reload needed", "verification command", "side effects".
- Atomic replace behavior and failed-syntax behavior are documented with evidence.
- Rollback is demonstrated for at least one Postfix change and one Dovecot change.
- Evidence stored in `docs/evidence/E1-09/`.

## How to test

```
# Example: P3, adding a mailbox "dave" to client.test (Postfix part)
# 1. Write the new entries to temporary files, rename over the live files
# 2. WITHOUT reloading, test:
swaks --server 127.0.0.1:2525 --from s@sender.test --to dave@client.test --body "test"
docker compose exec mta postconf -n | head -0   # sanity
docker compose exec mta postmap -q dave@client.test texthash:/config/postfix/recipient_bcc
# 3. Reload and test again:
docker compose exec mta postfix reload
# 4. Repeat the swaks test and inspect the logs and the mailbox

# Example: D2, password change
docker compose exec imap doveadm auth test alice@client.test OLD-PASS     # before: success
# edit the users file (new hash), then WITHOUT reload:
docker compose exec imap doveadm auth test alice@client.test NEW-PASS     # record result
docker compose exec imap doveadm reload
docker compose exec imap doveadm auth test alice@client.test NEW-PASS     # expect success
docker compose exec imap doveadm auth test alice@client.test OLD-PASS     # expect failure
```

## Notes and pitfalls

- Some services cache lookups for a short time. If a change appears to work after a few seconds with no reload, repeat the test several times at different delays, and record the worst case. An unreliable "it eventually works" is not a pass.
- Test with an **open IMAP connection** during a Dovecot reload to see whether sessions survive.
- Do not conclude from a single success. A change that works once because a previous test warmed a cache is a classic false pass. Reset the services (restart both) before each independent experiment.
- Record the exact command lines, because the Rust service will issue the same commands through the Docker API.
