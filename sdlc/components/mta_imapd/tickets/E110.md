# E1-10: Reference ("golden") configuration files and format spec

**Epic:** E1 (mta + imap prototype)
**Size:** M
**Depends on:** E1-06, E1-08, E1-09
**Hypotheses covered:** none (this is a deliverable ticket)

## Context

Later, the Rust `admin` service will **generate** every table and user file from its own state. The simplest way to know it generates the right content is to compare its output, character for character, against files that are known to work. This ticket produces those files and the written rules that describe them.

Without this ticket, the Rust author would have to reverse-engineer the working prototype. With it, they have a precise, tested contract.

## What to do

1. Create the folder `reference/` with the following structure:
   ```
   reference/
   ├── README.md                      what this folder is and how it is used
   ├── state/
   │   ├── settings.example.toml      example settings (see technical.md section 4.3)
   │   └── mail.example.toml          example domains and mailboxes (the fixtures)
   ├── generated/
   │   ├── postfix/
   │   │   ├── relay_domains
   │   │   ├── transport
   │   │   ├── virtual_mailboxes
   │   │   ├── recipient_bcc
   │   │   ├── relay_recipients
   │   │   └── sender_login
   │   └── dovecot/
   │       └── users
   └── FORMAT.md                      the rules (see step 3)
   ```
2. Fill the example state files with the fixtures from `EPIC.md` section 3. In `mail.example.toml`, use a placeholder where a real password hash goes, plus the hash actually used in the prototype so the generated Dovecot file can be compared exactly. Use a fixed, documented hash for tests so results are reproducible.
3. For every generated file, write its **format rules** in `FORMAT.md`. Each rule must be precise enough to implement without guessing:
   - Header comment text, exact wording (so output can be compared with a plain diff).
   - Line format, field separators, and quoting.
   - Ordering rule (for example, sorted alphabetically by domain, then by local part), so output is deterministic.
   - How the internal name is built from a mailbox: the separator `^`, where the domain goes, how `L` is appended, lowercase rules.
   - How a catch-all domain is represented, including the reserved local part `_catchall`.
   - How disabled domains are represented (omitted, or present and flagged). Decide and test it with Postfix.
   - What the files look like when **empty** (no domains yet, as on first start). Test that Postfix and Dovecot start and run correctly with empty files. This is essential because `admin` renders the initial config on first run.
   - File permissions and ownership each file needs.
   - Characters that must be rejected in user input (spaces, `^` in a local part or domain, control characters, uppercase handling), with reasoning for each.
4. Copy the final working files from `prototype/config/` into `reference/generated/`, normalize them to match `FORMAT.md` exactly (header comments, ordering), and **re-run the E1-11 scenario tests against the normalized files** to prove they still pass.
5. Write `reference/README.md` explaining that these files are the contract for the Rust render step, and that the snapshot tests in Epic 4 compare against them.
6. Add to `FORMAT.md` the **apply sequence** distilled from E1-09: for each kind of change, which files change, which reload commands run in which container, and which verification commands follow. This is the specification of the admin service's apply pipeline, in plain language.

## Acceptance criteria

- Every file type that the admin service will generate has an example in `reference/generated/` and a rule in `FORMAT.md`.
- Regenerating the example state by hand-following the `FORMAT.md` rules yields byte-identical files (have a second person, or a fresh pass by the same person, do this on one file and compare with `diff`).
- The normalized files, copied into `prototype/config/`, pass all scenario tests.
- The empty-file case is tested: both containers start and behave correctly with empty tables and an empty user file.
- `FORMAT.md` states the validation rules for every user-supplied value.
- `FORMAT.md` contains the apply sequence table.

## How to test

```
# Use the normalized files in the prototype
cp -r reference/generated/postfix/* prototype/config/postfix/
cp -r reference/generated/dovecot/* prototype/config/dovecot/
docker compose down && docker compose up -d --build
prototype/tests/run-all.sh                      # from E1-11, expect all pass

# Empty-case test
mkdir -p /tmp/empty && for f in relay_domains transport virtual_mailboxes recipient_bcc relay_recipients sender_login; do : > /tmp/empty/$f; done
# mount the empty files in place of the real ones, restart mta, and check:
docker compose exec mta postfix check
docker compose logs mta | tail -30              # no errors on start
```

## Notes and pitfalls

- A header comment with a timestamp makes output non-deterministic, which breaks snapshot tests. **No timestamps in generated files.**
- The order of lines in a table normally does not matter to Postfix, but deterministic order matters to humans and to tests. Specify it.
- If `texthash:` or the user file treats a trailing newline or Windows line endings differently from what you expect, record it. The specification must name the exact line ending.
- Do not hand-tune the golden files after tests pass without re-running the full scenario suite.

## Outputs

The `reference/` folder, `FORMAT.md`, and the apply sequence table.
