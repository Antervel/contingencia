# E1-11: Automated scenario test script

**Epic:** E1 (mta + imap prototype)
**Size:** M
**Depends on:** E1-05 (and grows with E1-06, E1-07, E1-08, E1-09)
**Hypotheses covered:** all, as regression protection

## Context

Every ticket in this epic proves something by hand. Manual evidence is fine once, but the same scenarios must be re-run after every configuration change, on every Debian update, and later in the full integration test of Epic 6. This ticket turns the manual scenarios into a script that anyone can run, with a clear pass or fail result per scenario.

Start this ticket early, right after E1-05, and add scenarios as each later ticket finishes. Do not wait until the end.

## What to do

1. Create `prototype/tests/run-all.sh` as the single entry point. It must:
   - bring the stack to a **known clean state** (empty queue, empty mailboxes, empty sink, `main` running),
   - run each scenario script in `prototype/tests/scenarios/` in numeric order,
   - print one line per scenario: PASS or FAIL, with its name,
   - on failure, print the relevant evidence (log excerpt, queue listing, mailbox listing),
   - exit with a non-zero code if any scenario fails.
2. Create the shared helper library `prototype/tests/lib/` (extending the sink helpers from E1-02) with functions to:
   - reset state (clear sink, clear mailboxes, purge the queue),
   - send a message to a given address (with or without authentication),
   - count messages in a mailbox over IMAP,
   - read a message from a mailbox,
   - count and list queued messages,
   - wait until a condition is true or a timeout expires (for example, "the sink has N messages"), because timing is the most common cause of flaky tests,
   - assert helpers that fail with a readable message ("expected 1 message in alice's INBOX, found 0").
3. Write one scenario script per behavior, numbered, each independent of the others and each resetting state first:

   | Scenario | Source ticket |
   |---|---|
   | 01 relay with `main` up | E1-04 |
   | 02 queue with `main` down | E1-04 |
   | 03 open-relay protection | E1-04 |
   | 04 copy to mailbox, `main` up | E1-05 |
   | 05 copy to mailbox, `main` down, original queued | E1-05 |
   | 06 visible headers of the copy | E1-05 |
   | 07 internal domain not injectable from outside | E1-05 |
   | 08 catch-all precedence | E1-06 |
   | 09 no catch-all in other.test | E1-06 |
   | 10 recipient policy: accept any | E1-06 |
   | 11 recipient policy: listed only | E1-06 |
   | 12 recovery: queued originals delivered when `main` returns | E1-07 |
   | 13 queue survives `mta` restart | E1-07 |
   | 14 authenticated submission works | E1-08 |
   | 15 wrong password rejected | E1-08 |
   | 16 sender enforcement | E1-08 |
   | 17 rate limit | E1-08 |
   | 18 port 25 unaffected by submission rules | E1-08 |
   | 19 reload table verification commands | E1-09 |
   | 20 empty configuration starts cleanly | E1-10 |

4. Make the script **deterministic**: no sleeps longer than needed, always wait on a condition with a timeout, and report the elapsed time per scenario.
5. Add a `--only N` option to run a single scenario, and a `--keep` option to leave the stack running after the run for inspection.
6. Add a short `prototype/tests/README.md`: prerequisites (which SMTP client and IMAP client are used), how to run, how to interpret failures, and how to add a scenario.

## Acceptance criteria

- `prototype/tests/run-all.sh` runs from a clean checkout after `docker compose up -d --build`, with no manual steps.
- Every scenario in the table exists and passes on the final configuration.
- A deliberate break (for example, delete the catch-all line from `recipient_bcc`) makes the relevant scenario fail with a readable message, and the script's exit code is non-zero. Demonstrate this with at least two different deliberate breaks, and record it.
- Running the suite **three times in a row** produces the same result each time (no flakiness). If a scenario is flaky, fix the waiting logic, not the expectation.
- Total run time is recorded in `FINDINGS.md` (target: a few minutes).

## How to test

```
docker compose up -d --build
prototype/tests/run-all.sh                  # all pass
prototype/tests/run-all.sh --only 08        # catch-all scenario only

# Deliberate break, to prove the tests can fail
sed -i '/@client.test/d' prototype/config/postfix/recipient_bcc
docker compose exec mta postfix reload
prototype/tests/run-all.sh --only 08        # must FAIL with a clear message
git checkout prototype/config/postfix/recipient_bcc
docker compose exec mta postfix reload
```

## Notes and pitfalls

- A test that cannot fail is worthless. The deliberate-break check is mandatory.
- Do not share state between scenarios. A scenario that passes only because a previous one left a message behind will hide bugs.
- Keep each scenario short and readable: a person reading it should understand what behavior is being protected in under a minute.
- The suite runs against the **real containers**, not mocks. That is its purpose.

## Outputs

`prototype/tests/run-all.sh`, helper library, 20 scenario scripts, test README, timing notes in `docs/FINDINGS.md`.
