# E1-13: CI/CD: build, test and publish images on push to `main`

**Epic:** E1 (mta + imap prototype)
**Size:** M
**Depends on:** E1-04 (both `mta` and `imap` images must exist). The test gate in Part B uses the suite from E1-11, so Part B is finished after E1-11.
**Hypotheses covered:** none (delivery requirement, PRD IR-8 and AC-13)

## Context

The PRD requires that the images we build are built and published **automatically by GitHub's CI/CD on every push to `main`**, only when the checks pass, and traceable to their commit (PRD IR-8, AC-13). Design details are in `technical.md` section 12.

This ticket creates the pipeline while only two images exist (`mta` and `imap`). That is deliberate: a pipeline with two images is simple to get right, and each later epic then adds one more image by adding one line to the build matrix. Setting it up late would mean nothing is published until Epic 5.

The `webmail` image is the upstream Roundcube image. It is **not** built by this pipeline, only pinned in the Compose file.

## What to do

### Part A: Build and publish

1. Create the workflow file `.github/workflows/images.yml` with these triggers:
   - push to `main`: build, test and publish;
   - pull request: build and test only, **never publish**;
   - manual run: behaves like a push to `main`.
2. Define the **build** stage as a matrix over the images, currently `mta` and `imap`. Adding an image later must be a one-line change.
3. Make the **same image** flow from build to test to publish. Do **not** rebuild between testing and publishing. Choose one way and document it in the workflow comments:
   - pass the built image between jobs as a build artifact and load it again; or
   - push it under a temporary tag and re-tag it after the tests pass.
4. Define the **publish** stage:
   - runs only on push (or manual run) on `main`;
   - runs only if build and test succeeded;
   - pushes to GitHub's container registry, one image per component, named after the repository (see `technical.md` 12.4);
   - sets the tags: the **full commit hash**, and `latest`;
   - sets standard image labels: source repository, commit hash, build time.
5. Use the **minimum permissions** for the workflow: read access to the repository by default, and write access to packages only in the publish job.
6. Pin every third-party action used in the workflow to a specific commit, not to a moving tag. Add a comment next to each with the human-readable version it corresponds to.
7. Set concurrency rules: a newer run for the same pull request cancels the older one; runs on `main` are never cancelled midway.
8. Pin the base image (the Debian release recorded in E1-01) by tag in both Dockerfiles, if not already done.
9. Add `compose.release.yaml`, which refers to the published `mta` and `imap` images through `image:` entries, with the tag controlled by a single variable. Pin `webmail` in the Compose files (a placeholder entry is enough until Epic 3 if it does not exist yet; note it in the file).

### Part B: Test gate

10. Add a **test** stage between build and publish. It starts the Compose stack from the images that were just built and runs these checks:
    - `postfix check` inside `mta`;
    - Dovecot configuration check inside `imap`;
    - both containers reach the healthy state within a timeout;
    - the scenario suite `prototype/tests/run-all.sh` (from E1-11).
    If E1-11 is not finished yet, gate on the first three checks and leave a clearly marked step in the workflow that runs the suite. **Complete this step as soon as E1-11 exists.** The epic cannot be closed (E1-12) until it is complete.
11. On failure, upload the logs from the containers and the test output as workflow artifacts, so a failure can be diagnosed without re-running.

### Part C: Documentation

12. Add a short `docs/CICD.md` covering:
    - what triggers a build and what does not;
    - the image names, tags and labels;
    - how to find which commit a running container was built from;
    - how to pin an install to a commit hash;
    - how to re-run a failed build;
    - how to add a new image to the pipeline.
13. Record in `docs/FINDINGS.md` the average build and test duration, and the final image sizes.

## Acceptance criteria

- A push to `main` with passing checks produces, with no manual step, a published `mta` and `imap` image, each tagged with the full commit hash and `latest`.
- A **pull request** builds and tests but publishes nothing. Prove it by opening a pull request and checking that no new package versions appeared.
- A **deliberately failing** change (for example, break a line in `recipient_bcc` so a scenario fails) pushed to a branch or pull request shows a failed test stage, and a push of the same breakage to `main` publishes **nothing** (do this with a temporary branch protected rule or a throwaway fork, and record the evidence). Remove the breakage afterwards.
- The image that was tested is identical to the image that was published (compare image digests recorded in the run).
- Each published image carries labels with the source repository, the commit hash and the build time.
- On a clean machine, with only the Compose files and the registry access, pulling the published images by commit hash and starting the stack with `compose.release.yaml` produces healthy `mta` and `imap` containers.
- The workflow's permissions are limited as described, and every third-party action is pinned to a commit. Review the file with that checklist and record the result.
- `docs/CICD.md` exists and a person who did not write the workflow can follow it to add a new image to the matrix.

## How to test

```
# After pushing to main
gh run list --workflow images.yml --limit 5
gh run view <run-id> --log-failed                   # only if it failed

# On any machine with registry access
docker pull <registry>/<owner>/<repo>/mta:<full-commit-hash>
docker pull <registry>/<owner>/<repo>/imap:<full-commit-hash>
docker inspect --format '{{ json .Config.Labels }}' <registry>/<owner>/<repo>/mta:<full-commit-hash>
docker image inspect --format '{{ .Id }}' <image>     # compare with the digest the run recorded

# Run the published stack
CONTINGENCY_TAG=<full-commit-hash> docker compose -f compose.release.yaml up -d
docker compose -f compose.release.yaml ps             # both healthy

# Deliberate break (on a throwaway branch)
sed -i '/@client.test/d' prototype/config/postfix/recipient_bcc
git commit -am "break catch-all on purpose" && git push origin HEAD
# Expect: test stage fails; no new image tag appears in the registry
```

## Notes and pitfalls

- The first publish to the container registry creates the package with default settings that may not match what you want. Check its **visibility** and its **link to the repository** after the first run, and adjust the package settings. Record the final settings.
- Pull requests from forks do not get write access by design. This pipeline only publishes from `main`, so that is expected. Do not weaken it to make forks publish.
- Running Compose on the CI runner needs the same published ports as the prototype, bound to the runner's local interface. Make sure the suite's host ports do not collide with anything on the runner.
- Timing issues are the most common cause of flaky CI. The suite already waits on conditions with timeouts (E1-11). Do not add fixed sleeps to the workflow to fix a flaky run.
- Do not publish from pull requests, and do not tag `latest` anywhere except from `main`.
- Decide, and record, which architecture the images are built for. Default is the architecture of the client's servers (normally `amd64`). If the client uses ARM, tell the epic owner before building multi-architecture images, because it changes build time and the test setup.
- If the sealed environment cannot pull from the registry, the images must be moved by other means. That is not part of this ticket, but raise it with the epic owner as soon as it is known (see `technical.md` 12.7).
